# Can an agent send a Message through a command-line tool run from its shell, instead of an MCP server?

Research for issue #182 (parent map #170, Messages between Terminals; blocks #183). Researched 2026-11-09. Builds on #171 (`docs/research/tool-server-registration.md`), #172 (`tool-server-caller-identity.md`), #173 (`held-open-tool-calls.md`) and #174 (`provider-typed-input.md`), each on its own `research/<slug>` branch. Those notes are not repeated; where this one compares with them it says so.

## Question

Instead of registering an MCP server in each Provider's config, a `timmy` command on the PATH of every Terminal Timmy starts could send the Message: the agent runs it in its shell, and the command talks to Timmy in main. For Claude Code, OpenCode and Codex, from primary sources:

- (a) does the shell tool the agent runs commands in pass Timmy's environment variables through (`TIMMY_TERMINAL_ID`, a per-Terminal secret), given any default name filtering (KEY, SECRET, TOKEN)?
- (b) can a command inside the Provider's sandbox reach a loopback server or a named pipe?
- (c) does each run need the user's approval, and can an allow rule for only Timmy's command be written, and where?
- (d) what shell-command timeout applies while the command blocks for the user's decision, compared with #173?
- (e) how does the agent learn the command exists: an agent skill Timmy installs (user-level folders, install and removal touching only Timmy's file, can the description limit it to a Timmy Terminal), instruction files, or `--help`? Include how Orca does it as a worked example.
- (f) on Windows, how does a command on the PATH of Timmy's Terminals resolve, and does it stay inert outside them?

## Short answer

- **(a) Yes on all three by default, with three opt-in ways for a user to lose it.** Claude Code and OpenCode hand the shell tool the full environment (Claude Code's scrub is opt-in). Codex defaults to `inherit = "all"` and does **not** apply its KEY/SECRET/TOKEN filter by default (`ignore_default_excludes` defaults to `true`), but a user's `inherit = "core"`, `include_only` or `ignore_default_excludes = false` drops `TIMMY_*`, and Orca's source already works around exactly this.
- **(b) Only Codex's default sandbox blocks it, and it blocks both.** Codex `workspace-write` has network off; its Linux filter denies `connect()` for every address family, so loopback and a Unix socket both fail (Orca recorded a real `EPERM` against Codex 0.165.0). Claude Code's sandbox is off by default and absent on native Windows; OpenCode has no sandbox.
- **(c) Claude Code and Codex can pre-approve exactly Timmy's command; OpenCode needs no rule by default.** Claude Code: `Bash(timmy send *)` in `permissions.allow` of `~/.claude/settings.json`. Codex: a `prefix_rule(..., decision = "allow")` in a Timmy-owned `~/.codex/rules/timmy.rules`, and that rule also takes the command **out of the sandbox**, which fixes (b). OpenCode: bash defaults to `allow`; a `permission.bash` pattern only matters if the user set `ask`.
- **(d) The shell is a worse place to hold a call than an MCP server on two of three Providers.** Claude Code moves a foreground command to the background at 2 minutes (not killed); OpenCode kills it at 2 minutes by default; Codex returns control after 10 to 30 seconds and the agent must poll. All three can be given more time, but only by the agent or by user-level settings. Orca avoids the problem: its `ask` returns at once and Orca wakes the agent later. Inference: Timmy's "queued" outcome can do the same.
- **(e) A skill works on all three, from user-level folders, and one shared file reaches two Providers.** Codex and OpenCode both read `~/.agents/skills/<name>/SKILL.md`; Claude Code reads only `~/.claude/skills/<name>/` (its docs never mention `.agents`). Removal is deleting Timmy's own folder. No Provider can gate a skill on an environment variable, so "only inside a Timmy Terminal" is prose the model must obey.
- **(f) Prepending a directory to the PATH Timmy gives its own PTYs keeps the command inert elsewhere, and Orca ships exactly that.** On Windows ship a native `.exe` (and an extensionless script for Git Bash); a `.cmd` has quoting limits and Git Bash may not find it.

## Findings per Provider

### Claude Code

**(a) Environment.** The Bash and PowerShell tools run with the environment Claude Code has: the sandbox page's table says environment variables are "Inherited from Claude Code, including any secrets in its environment" ([sandboxing, "What the sandbox restricts"](https://code.claude.com/docs/en/sandboxing)). The Bash tool does not carry `export`s from one command to the next ([tools-reference, "What persists between commands"](https://code.claude.com/docs/en/tools-reference)), which does not matter for variables set before launch. The opt-in `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` "strip[s] credentials from the environments of the subprocesses Claude Code starts, such as Bash commands, hooks, and stdio MCP servers", recognising a credential "by its variable name or by the shape of its value"; the examples removed are `ANTHROPIC_API_KEY`, `AWS_SECRET_ACCESS_KEY`, `NPM_TOKEN`, `DB_PASSWORD`, `CLAUDE_CONFIG_DIR` and a `DATABASE_URL` containing a password; `GITHUB_TOKEN`, `GH_TOKEN` and proxy variables are kept ([env-vars, "What the subprocess environment scrub removes"](https://code.claude.com/docs/en/env-vars)). The docs give no name pattern, so whether `TIMMY_TERMINAL_SECRET` would be removed is **Not verified**; a name with TOKEN or PASSWORD in it is the likeliest to be. **Precedent:** Claude Code itself exports a per-session `CLAUDE_CODE_MESSAGING_TOKEN` and `CLAUDE_CODE_MESSAGING_SOCKET` "to hooks and Bash commands", so that "a script posting to the socket can send `{"type":"auth","token":"<token>"}`" ([env-vars](https://code.claude.com/docs/en/env-vars), [cross-session-messaging, "The session's inbox socket"](https://code.claude.com/docs/en/cross-session-messaging)). That is the same pattern as this ticket, built by the Provider, with a named pipe on native Windows.

**(b) Sandbox.** Off by default (`sandbox.enabled`), and "On native Windows, Claude Code runs commands unsandboxed"; it exists on macOS, Linux and WSL2 ([sandboxing](https://code.claude.com/docs/en/sandboxing)). With it on, shell commands have "No direct route out": connections go through a proxy checking hosts against `allowedDomains`, which start empty; the proxy refuses a hostname that resolves only to local addresses, except `localhost` and `*.localhost`, and an IP can be allowed as `"127.0.0.1:8080"` (sandboxing, "Hostnames that resolve to local addresses"). Per [settings-reference](https://code.claude.com/docs/en/settings-reference): `network.allowLocalBinding` lets sandboxed commands on macOS connect to localhost and "has no effect on Linux and WSL2, where each sandboxed command has its own loopback interface"; `allowUnixSockets` (paths) works only on macOS, and on Linux and WSL2 "the seccomp filter can't inspect socket paths", so only `allowAllUnixSockets` opens them. The messaging page says the same settings control whether a Bash command can reach Claude Code's own inbox socket. Named pipes: no sandbox exists on Windows, so none is blocked there; whether a macOS or Linux sandbox restricts anything beyond the sockets listed is **Not verified**. Local MCP servers, hooks and file tools "run outside" the sandbox (sandboxing, "What runs outside the sandbox"); a shell command does not.

**(c) Approval.** Bash commands go through the permission flow. Rules are evaluated deny, then ask, then allow; a `*` matches any text; "a `*` at the end, with a space before it, also matches the bare command", so `Bash(timmy send *)` matches `timmy send ...` and `timmy send`, not `timmyx` ([permissions, "Wildcard patterns"](https://code.claude.com/docs/en/permissions)). Compound commands are split on `&&`, `||`, `;`, `|`, `|&`, `&` and newlines and every part must be allowed; "an allow rule won't match past an assignment of any other variable", so `FOO=1 timmy send` prompts. A form the rule does not match, such as `/usr/bin/timmy` or `sh -c 'timmy ...'`, falls back to a prompt (permissions, "What a Bash rule doesn't match", which discusses deny rules; for an allow rule the same non-match means a prompt, which is the safe side). Where: allow rules live in the `permissions.allow` array of a settings file; user scope is `~/.claude/settings.json` (`%USERPROFILE%\.claude` on Windows) and applies to every project ([settings](https://code.claude.com/docs/en/settings)); project-scope allow rules wait for workspace trust. A skill's `allowed-tools: Bash(timmy send *)` pre-approves the call for the turn that invoked the skill only; "The grant clears when you send your next message" ([skills, "Pre-approve tools for a skill"](https://code.claude.com/docs/en/skills)). In sandbox auto-allow mode a sandboxed command needs no prompt, but a host outside `allowedDomains` does. **Inference:** the settings entry is the same kind of edit as ADR 0009's Hook entry, so Timmy can add and remove one array element it owns; a user's own broader `ask` or `deny` rule would still win ("an allow rule can't carve an exception out of a deny rule").

**(d) Timeout.** A foreground Bash or PowerShell command defaults to 2 minutes (`BASH_DEFAULT_TIMEOUT_MS` 120000); the model may pass a longer `timeout`, capped by `BASH_MAX_TIMEOUT_MS` (default 10 minutes; the effective ceiling is the larger of the two). "When a foreground command reaches its timeout without finishing, Claude Code moves it to the background instead of stopping it", and the result says `Command did not complete within its 120s timeout and was moved to the background`, with a task ID and the output file path ([tools-reference, "Timeout and output limits", "Foreground commands that move to the background"](https://code.claude.com/docs/en/tools-reference)). A local interactive session puts no time limit on background commands. The variables can be set in the `env` block of `settings.json`, but that changes Claude Code outside Timmy too. **Compared with #173:** an MCP call has a wall clock of about 28 hours and is auto-backgrounded after 2 minutes; the shell command is likewise backgrounded after 2 minutes but its hard ceiling for a held foreground call is 10 minutes by default. Whether the agent is told when a backgrounded command finishes, and whether Claude "starts on it unprompted" when idle, is **Not verified** in the pages read (#173 found it documented for MCP tasks only).

**(e) How the agent learns the command exists.** A personal skill is `~/.claude/skills/<skill-name>/SKILL.md`, loaded in all projects (not in Cowork or cloud sessions). "Claude Code watches skill directories for file changes": add, edit or remove under `~/.claude/skills/` is picked up in the running session, except that a top-level `skills` directory that did not exist at session start needs `/reload-skills`. To remove: "delete the skill's directory". A `<skill-name>` entry "can be a symlink to a directory elsewhere" ([skills, "Choose where skills load", "Edit a skill during a session", "Remove a skill"](https://code.claude.com/docs/en/skills)). Claude Code reads `~/.claude/skills`; its docs do not list `~/.agents/skills` (a search of the page for `.agents` finds nothing). Frontmatter: `description` ("What the skill does and when to use it"; combined with `when_to_use` it is cut at 1,536 characters in the listing), `disable-model-invocation`, `allowed-tools`, `paths` (file globs, not environment). There is **no field that gates a skill on an environment variable**, so "use this only inside a Timmy Terminal" can only be prose in the description and body, which the model decides whether to follow. **Inference:** a `` !`command` `` placeholder in the body runs before the content reaches Claude ([skills, "Inject dynamic context"](https://code.claude.com/docs/en/skills)) and could print whether `TIMMY_TERMINAL_ID` is set, giving the model a fact instead of an instruction; it works only once the skill has been invoked, and only in Claude Code. The listing has a budget (1% of the context window) and drops descriptions when full, so a Timmy skill costs a line in every session, Timmy or not. Instruction files: `~/.claude/CLAUDE.md` is the user's own file, and `~/.claude/rules/` is a user-level rules directory ([memory](https://code.claude.com/docs/en/memory)); a Timmy-owned file in the latter would touch no file of the user's. `--help` only helps once the agent already knows to run `timmy`.

**(f) Windows.** Claude Code routes shell commands through Git Bash unless the PowerShell tool is enabled (on by default without Git Bash; on by default with it for claude.ai and Console accounts), and it spawns PowerShell with `-ExecutionPolicy Bypass` by default so `.ps1` files run ([tools-reference, "PowerShell tool"](https://code.claude.com/docs/en/tools-reference), [env-vars `CLAUDE_CODE_POWERSHELL_RESPECT_EXECUTION_POLICY`](https://code.claude.com/docs/en/env-vars)). Resolution of `timmy` therefore depends on which shell the model uses; see "Windows" below. Denying `Bash` while Git Bash exists also turns the PowerShell tool off (tools-reference), so an allow rule must be written for each tool Timmy wants to pre-approve: `Bash(timmy send *)` and `PowerShell(timmy send *)` (PowerShell rules use the same shape and are case-insensitive; permissions, "PowerShell").

**Other finding, outside the question:** Claude Code already ships its own `SendMessage` and `ListAgents` between sessions on the same machine, on by default from v2.1.224 (macOS, Linux) and v2.1.234 (native Windows), delivering into an idle session by starting a turn and into a running one between tool calls ([cross-session-messaging](https://code.claude.com/docs/en/cross-session-messaging)). It has no Timmy Messaging rules, so it bypasses the map's rule model for Claude Code Terminals. A user can turn it off with `permissions.deny` on `SendMessage` and `ListAgents` and `crossSessionInbound: refuse` (same page). The map may want to decide whether Timmy leaves it alone or switches it off.

### Codex

**(a) Environment.** The shell tool builds its environment from `shell_environment_policy`. The source default is `inherit: All` and `ignore_default_excludes: true` ([`config_types.rs` L261-L272](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/protocol/src/config_types.rs#L261-L272)), and the docs agree: "`ignore_default_excludes` defaults to `true`, so Codex doesn't automatically remove variable names containing `KEY`, `SECRET`, or `TOKEN`" ([config-advanced, "Shell environment policy"](https://learn.chatgpt.com/docs/config-file/config-advanced)). So by default `TIMMY_*` reaches the command, secret-looking names included. The unified-exec shell path calls `create_env` with that policy ([`unified_exec/process_manager.rs` L1495-L1496](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/core/src/unified_exec/process_manager.rs#L1495-L1496)). A user's own config can drop it: `ignore_default_excludes = false` removes `*KEY*`, `*SECRET*` and `*TOKEN*` case-insensitively; `inherit = "core"` keeps only a fixed list (Unix: `PATH SHELL TMPDIR TEMP TMP HOME LANG LC_ALL LC_CTYPE LOGNAME USER`); `include_only` keeps only matches; `set` runs after the excludes ([`shell_environment.rs` L105-L190](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/protocol/src/shell_environment.rs#L105-L190)). `set` "can restore an excluded variable" and an include allowlist can still remove it again (docs). Codex also sets `CODEX_THREAD_ID`, `CODEX_SESSION_ID` and `CODEX_TOOL_CALL_ID` on the command. **Evidence from Orca:** its CLI says that "Codex sets CODEX_THREAD_ID after the env filter that can drop Orca identity" and tells the user to start Codex by typing `codex` in an Orca terminal or set `inherit = "all"` with `include_only` listing `"ORCA_*"` ([`terminal-identity.ts` L210-L231](https://github.com/stablyai/orca/blob/3ce8d75ae98c6d18892d8ef316fb2a7eb2992c77/src/cli/handlers/orchestration/terminal-identity.ts#L210-L231)). Timmy cannot widen a user's policy for only its own names without editing the user-owned `[shell_environment_policy]` table, so the command must fail closed with a clear message when `TIMMY_TERMINAL_ID` is missing.

**(b) Sandbox.** The default local mode is `workspace-write` with "network access turned off" ([agent-approvals-security, "Network access"](https://learn.chatgpt.com/docs/agent-approvals-security)). On Linux, bubblewrap adds `--unshare-net` when network is restricted, and the seccomp filter in `Restricted` mode denies `connect`, `bind`, `listen`, `accept`, `sendto` and others for every family; it allows `socket(AF_UNIX)` but not `connect` ([`linux-sandbox/README.md`](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/linux-sandbox/README.md), [`seccomp.rs` L203-L233](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/linux-sandbox/src/seccomp.rs#L203-L233)). **Inference:** a loopback TCP connect and a Unix-socket connect to Timmy both fail in the default Linux sandbox. Real evidence: Orca captured Codex 0.165.0 on Linux with `workspace-write` and `network_access = false` and recorded `orca status --json` failing with a permission error on connect ([`runtime-access-denied.ts`](https://github.com/stablyai/orca/blob/3ce8d75ae98c6d18892d8ef316fb2a7eb2992c77/src/cli/runtime/runtime-access-denied.ts), fixture `fixtures/codex-0.165.0-linux-connect-denied.json`). Loopback is also refused by the optional network proxy: `allow_local_binding = false` "blocks loopback, link-local, and private destinations" unless an exact local IP or `localhost` is allowed (agent-approvals-security, "Local and private destinations"). Windows has three sandboxes: `mxc` (recommended, "native process isolation without administrator-approved setup"), `elevated`, and `unelevated` (weaker network isolation) ([windows-sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox)). The page says only that "MXC permits connections to and from services on host loopback" in the managed-networking context; whether a plain `workspace-write` command can reach loopback or a **named pipe** on any of the three, and what macOS Seatbelt allows without the network policy, is **Not verified**.

**(c) Approval.** In the `Auto` preset "Codex can read files, make edits, and run commands in the working directory automatically" and asks "to run commands that require network access" (agent-approvals-security). So without a rule a sandboxed `timmy` call either fails on (b) or triggers an escalation prompt. Rules: a `.rules` file under `rules/` next to an active config layer, for example `~/.codex/rules/default.rules`; `prefix_rule(pattern = ["timmy", "send"], decision = "allow")`, where `allow` means "Run the command outside the sandbox without prompting"; "Codex applies the most restrictive decision when more than one rule matches"; a restart is needed ([rules](https://learn.chatgpt.com/docs/agent-configuration/rules)). The loader takes any file whose extension is `rules` ([`exec_policy.rs` L56-L57, L1212](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/core/src/exec_policy.rs#L1212)), so Timmy can own `~/.codex/rules/timmy.rules` and delete it to deactivate, while allow-list additions made in the TUI go to `default.rules`. **Consequences, Inference:** (1) one rule fixes both approval and the sandbox block, but it makes the command run unsandboxed, which is acceptable only because the command is Timmy's own; (2) Codex matches the argument vector, and a shell wrapper is split only when it is "a linear chain of commands made only of plain words ... joined by safe operators"; a script with redirection, `$(...)`, `VAR=...` or wildcards is matched as one `["bash","-lc","<script>"]` invocation (rules, "Shell wrappers and compound commands"). So a Message passed through a heredoc, stdin redirect or command substitution may not match `["timmy","send"]` and would prompt each time. Whether a quoted `--body "..."` argument counts as a plain word is **Not verified**; `codex execpolicy check` tests it offline (see Unknowns).

**(d) Timeout.** The default shell tool is unified exec (`unified_exec` is `Stable`, `default_enabled: true`, [`features/src/lib.rs` L1167-L1171](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/features/src/lib.rs#L1167-L1171)). `exec_command` waits `yield_time_ms` (default 10000, effective range 250 to 30000; on Windows 10000 to 30000) and then returns a session ID for a still-running command; the model must call `write_stdin` to poll, each empty poll waiting 5 s up to `background_terminal_max_timeout` (default 300000 ms) ([`shell_spec.rs` L27-L30](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/core/src/tools/handlers/shell_spec.rs#L27-L30), [`unified_exec/mod.rs` L66-L71](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/core/src/unified_exec/mod.rs#L66-L71), [config-reference `background_terminal_max_timeout`](https://learn.chatgpt.com/docs/config-file/config-reference)). I found no wall-clock kill of such a process, only pruning past 64 processes (`process_manager.rs`, `prune_processes_if_needed`) and termination on denial, interrupt or exit. **Inference:** a blocking `timmy` call is not killed while the user decides, but the agent gets control back after at most 30 s and keeps the Message "in flight" unless it polls. The older exec path has `DEFAULT_EXEC_COMMAND_TIMEOUT_MS = 10_000` ([`exec.rs` L63](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/core/src/exec.rs#L63)); which models still use it is **Not verified**. **Compared with #173:** MCP is 300 s in source (60 s in the docs) per call, raisable per entry; here nothing is raisable by Timmy, and the design is "return early, poll".

**(e) How the agent learns the command exists.** Skills: user scope is `$HOME/.agents/skills` ([build-skills, "Where Codex loads local skills"](https://learn.chatgpt.com/docs/build-skills)); the source also keeps the deprecated `$CODEX_HOME/skills` ([`host_roots.rs` L135-L146](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/ext/skills/src/host_roots.rs#L135-L146)). A skill is a folder with `SKILL.md` (`name` and `description` required); "Codex detects skill changes automatically. If an update doesn't appear, restart Codex"; symlinked skill folders are followed; `agents/openai.yaml` can set `policy.allow_implicit_invocation: false`; `[[skills.config]]` with `path` and `enabled = false` in `~/.codex/config.toml` disables a skill without deleting it (a table in a file Timmy does not own). The listing is `name`, `description` and file path, within 2% of the context window by default, "Codex shortens skill descriptions first" and may omit skills with a warning. Implicit use depends on `description` ("Front-load the key use case and trigger words"). As in Claude Code, no environment gate exists. Instruction files: the global `~/.codex/AGENTS.override.md`, else `AGENTS.md`, and "Codex uses only the first non-empty file at this level" ([agents-md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)), so Timmy cannot add a file of its own there without taking over the user's.

**(f) Windows.** The shell policy for `inherit = "core"` keeps `PATH`, `PATHEXT`, `COMSPEC` and other Windows core variables, and Codex adds a default `PATHEXT` of `.COM;.EXE;.BAT;.CMD` if none survives ([`shell_environment.rs`](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/protocol/src/shell_environment.rs#L105-L190)). Codex runs the default shell on Windows ("Codex uses the native Windows sandbox when you run in PowerShell", [sandboxing](https://learn.chatgpt.com/docs/sandboxing)); which shell it chooses is **Not verified**.

### OpenCode

**(a) Environment.** In v2.2.6, `Shell.create` starts the command with `{ ...baseEnv, TERM, OPENCODE_TERMINAL }` where `baseEnv` is the session's environment or `process.env`, and the bash tool adds `AGENT=1`, `OPENCODE=1`, `AI_AGENT` and `OPENCODE_SESSION_ID` ([`shell.ts` L267-L283](https://github.com/anomalyco/opencode/blob/v2.2.6/packages/core/src/shell.ts#L267-L283), [`tool/plugin/shell.ts` L196-L204](https://github.com/anomalyco/opencode/blob/v2.2.6/packages/core/src/tool/plugin/shell.ts#L196-L204)). No name filter exists in that path. In v1.19.5 the environment is `{ ...process.env, ...extra.env }` where `extra.env` comes from a plugin `shell.env` hook ([`tool/shell.ts` L416-L424](https://github.com/anomalyco/opencode/blob/v1.19.5/packages/opencode/src/tool/shell.ts#L416-L424)). So `TIMMY_*`, secret-looking names included, reaches the command on both lines.

**(b) Sandbox.** None found. The docs have no sandbox feature (a search of the docs folder for "sandbox" finds only a third-party plugin in `ecosystem.mdx`), and the command is a plain child process (`environment.spawner.spawn(ChildProcess.make(invocation.shell, args, ...))`, `shell.ts` L309-L316). **Inference:** loopback, Unix sockets and named pipes are reachable unless the OS or the user restricts them. This is an absence claim from docs and two code paths.

**(c) Approval.** "Most permissions default to `allow`" and only `doom_loop` and `external_directory` default to `ask` ([permissions, "Defaults"](https://github.com/anomalyco/opencode/blob/v2.2.6/packages/web/src/content/docs/permissions.mdx)), so by default a `timmy` call is not prompted. If the user set `bash: ask`, a pattern rule `permission.bash["timmy *"] = "allow"` works: patterns use `*` and `?`, "the last matching rule wins", and bash patterns match parsed commands such as `git status --porcelain`. The rule lives in `permission` of `opencode.json` (global `~/.config/opencode/opencode.json`, or project), and agent-level `permission` is merged and takes precedence. "Always" approvals last only "for the rest of the current OpenCode session" (docs). **Inference:** because order matters, Timmy's key must come after any catch-all `"*"` key in the same object; how `permission.bash` objects from several config files merge and in what order is **Not verified**. A user's `--auto` mode approves anything not explicitly denied.

**(d) Timeout.** v2.2.6: `DEFAULT_TIMEOUT_MS = 2 * 60 * 1000` for foreground commands; the model may pass `timeout` (ms) and "Set to 0 to disable the timeout"; "background commands have no timeout by default", return at once and "you will be notified when they complete" ([`tool/plugin/shell.ts` L22, L52-L53, L188](https://github.com/anomalyco/opencode/blob/v2.2.6/packages/core/src/tool/plugin/shell.ts#L22)). On timeout "A recorded timeout must always kill" ([`shell.ts` L379](https://github.com/anomalyco/opencode/blob/v2.2.6/packages/core/src/shell.ts#L379)) and the output gets "Command exceeded timeout of N ms". v1.19.5: default 2 minutes, `timeout` parameter, and on expiry the command is killed and the result says "shell tool terminated command after exceeding timeout" ([`tool/shell.ts` L347, L540-L564](https://github.com/anomalyco/opencode/blob/v1.19.5/packages/opencode/src/tool/shell.ts#L540-L564)). **Compared with #173:** MCP is 60 s on v1 and 12 h on v2; the shell is 2 minutes on both, killed, and raising it is the model's choice per call, not Timmy's per entry. A held `timmy` call that outlives the timeout dies without delivering.

**(e) How the agent learns the command exists.** Skills are searched in `.opencode/skills`, `~/.config/opencode/skills`, `.claude/skills`, `~/.claude/skills`, `.agents/skills` and `~/.agents/skills` ([skills](https://github.com/anomalyco/opencode/blob/v2.2.6/packages/web/src/content/docs/skills.mdx)). So **one file at `~/.agents/skills/<name>/SKILL.md` is read by both Codex and OpenCode**, and OpenCode also reads the Claude Code folder. Frontmatter: `name` (lowercase, hyphens, must match the folder), `description` (1 to 1024 characters); "Unknown frontmatter fields are ignored". Skills are listed in the `skill` tool's description (`<available_skills>` with name and description) and loaded by `skill({ name })`; `permission.skill` patterns can allow, ask or deny, and `deny` "hides" a skill from the agent. No environment gate exists. If the same name sits in several locations the docs say to "Ensure skill names are unique across all locations", so installing the same skill into both `~/.agents/skills` and `~/.claude/skills` (needed for Claude Code) may clash in OpenCode; **Not verified**, but a symlink from one to the other, which Orca's installer plans around by "real path", is one answer. Instruction files: global rules in `~/.config/opencode/AGENTS.md` (first match wins per category) or the user's `~/.claude/CLAUDE.md`; the config `instructions` array takes file paths ([rules](https://github.com/anomalyco/opencode/blob/v2.2.6/packages/web/src/content/docs/rules.mdx)), a key Timmy could add its own file to.

**(f) Windows.** The v2 shell selector tries `$SHELL` if compatible, otherwise `pwsh`, `powershell`, Git Bash, then `COMSPEC` or `cmd.exe` ([`shell/select.ts` L99-L110, L174-L183](https://github.com/anomalyco/opencode/blob/v2.2.6/packages/core/src/shell/select.ts)). A `timmy` command must therefore resolve in PowerShell, Git Bash and cmd.exe. v1's selection was not read.

### Orca (worked example)

Orca hosts agent CLIs in terminals and gives agents an `orca` command-line tool plus skills. It does not use an MCP server for this: its docs route agent messaging and terminal control through `orca orchestration ...` and `orca terminal ...`, and its "MCP" setting registers external servers for agents ([cli/skills.mdx, "MCP servers"](https://github.com/stablyai/orca/blob/3ce8d75ae98c6d18892d8ef316fb2a7eb2992c77/docs/site/content/docs/cli/skills.mdx)). (I did not search Orca's whole source for an MCP server of its own.)

**The command and its PATH.** The CLI ships in the app and is registered globally under Settings, General, Orca CLI. On top of that, Orca prepends its launcher's directory to the `PATH` of every PTY it manages: "Orca puts a shim on the `PATH` of the terminals it manages" ([install.mdx](https://github.com/stablyai/orca/blob/3ce8d75ae98c6d18892d8ef316fb2a7eb2992c77/docs/site/content/docs/install.mdx)); the code is `prependOrcaCliDirToChildPath`, "PTY and structured children must reach this app's CLI regardless of global registration", and it also exports `ORCA_CLI_COMMAND` with the launcher's absolute path "so children can bypass login shells that reorder PATH" ([`orca-cli-child-path.ts`](https://github.com/stablyai/orca/blob/3ce8d75ae98c6d18892d8ef316fb2a7eb2992c77/src/main/cli/orca-cli-child-path.ts)). The name `orca` collides on Linux with GNOME's screen reader (`/usr/bin/orca`), so the globally installed command is `orca-ide` there, and the managed terminals get a shim so bare `orca` still works inside them (install.mdx). The skills carry the resolution rule: use `ORCA_CLI_COMMAND`, else `orca-dev` in a dev checkout, else `orca-ide` on Linux outside a managed terminal ("Never run bare `orca` there"), else `orca` ([`skills/orca-cli/SKILL.md`](https://github.com/stablyai/orca/blob/3ce8d75ae98c6d18892d8ef316fb2a7eb2992c77/skills/orca-cli/SKILL.md)).

**Windows.** The launcher prepended on Windows is the native `resources/bin/orca.exe`; the code comment says "`orca.cmd` refuses message bodies cmd.exe would mangle" ([`orca-cli-child-path.ts` L76](https://github.com/stablyai/orca/blob/3ce8d75ae98c6d18892d8ef316fb2a7eb2992c77/src/main/cli/orca-cli-child-path.ts#L76), [`bundled-cli-launcher-path.ts`](https://github.com/stablyai/orca/blob/3ce8d75ae98c6d18892d8ef316fb2a7eb2992c77/src/main/cli/bundled-cli-launcher-path.ts)). It finds the existing spelling of the PATH key (`Path` versus `PATH`) before writing it, "so merging cannot resurrect a shadow PATH key" ([`windows-path-segment-merge.ts`](https://github.com/stablyai/orca/blob/3ce8d75ae98c6d18892d8ef316fb2a7eb2992c77/src/main/pty/environment/windows-path-segment-merge.ts)).

**Identity and transport.** The caller is `ORCA_TERMINAL_HANDLE` from the environment (plus `ORCA_PANE_KEY`), sent as `from`; `--from` can override it, and the refusal text says "another pane's handle would act on its mailbox" ([`message-send-handler.ts`](https://github.com/stablyai/orca/blob/3ce8d75ae98c6d18892d8ef316fb2a7eb2992c77/src/cli/handlers/orchestration/message-send-handler.ts), `terminal-identity.ts`). The CLI reaches the app over a Unix socket or a Windows named pipe, using an `authToken` read from a runtime metadata file in the user-data directory (`ORCA_USER_DATA_PATH` or the platform default) ([`metadata.ts`](https://github.com/stablyai/orca/blob/3ce8d75ae98c6d18892d8ef316fb2a7eb2992c77/src/cli/runtime/metadata.ts), `shared/runtime-bootstrap.ts`). **Inference:** that token is per app, not per Terminal, and readable by any process of the same OS user, so in the CLI sources I read nothing stops a Terminal passing another Terminal's handle; the server side was not audited. This is the forgeable shape #172 warned about; Timmy's per-Terminal secret would be an improvement over Orca's.

**Sandbox handling.** When the socket connect fails with `EPERM` or `EACCES` the CLI returns `runtime_access_denied`, with wording specific to `CODEX_SANDBOX`: "The Codex sandbox blocked this command from connecting to Orca ... Orca may be running normally", and next steps "Retry through Codex's existing escalation ... Do not restart Orca" ([`runtime-access-denied.ts`](https://github.com/stablyai/orca/blob/3ce8d75ae98c6d18892d8ef316fb2a7eb2992c77/src/cli/runtime/runtime-access-denied.ts)). The skill stub repeats it to the agent: "re-run it with escalated permissions, and do not run `ORCA open` or restart Orca". So Orca did not solve (b); it detects it and tells the agent to escalate.

**Skills: how the agent learns, and how they are installed.**
- The public skills are "hybrid discovery stubs: short `SKILL.md` files that tell the agent _when_ to engage Orca and how to load the full guide from the running CLI", so "Command flags live in the binary so they cannot drift from the app version" (`cli/skills.mdx`, "Hybrid stubs vs the live guide"). The stub says to run `ORCA skills get <name>`; `ORCA agent-context --json` gives a machine-readable command schema.
- Descriptions are long and written as triggers with scope and an explicit counter-case ("Otherwise prefer your own subagents", [`skills/orchestration/SKILL.md`](https://github.com/stablyai/orca/blob/3ce8d75ae98c6d18892d8ef316fb2a7eb2992c77/skills/orchestration/SKILL.md)). There is no environment gate; the stub instead handles "Orca is not running" (`ORCA open --json`) and a missing guide.
- Install: `npx skills add https://github.com/stablyai/orca --skill orca-cli --global`, or `orca skills install` headless, or the app. Targets are a shared `~/.agents/skills` root plus an agent folder for agents that need one; Orca's provider table gives Claude Code `~/.claude/skills` and gives Codex and OpenCode no separate folder (they read the shared root) ([`skill-install-providers.ts`](https://github.com/stablyai/orca/blob/3ce8d75ae98c6d18892d8ef316fb2a7eb2992c77/src/shared/skill-install-providers.ts)). That agrees with the Providers' own docs above.
- Update and removal touch only Orca's own copies: "A copy counts as Orca's untouched copy when its folder holds only `SKILL.md` and that file matches a version Orca has shipped. Only those copies are rewritten ... Anything else is left alone and reported ... Orca never deletes a folder it did not create"; a replaced edited copy is first moved to `~/.agents/.orca-skill-backups/` (`cli/skills.mdx`, "Keep skills up to date"; classifier in [`bundled-skill-classification.ts`](https://github.com/stablyai/orca/blob/3ce8d75ae98c6d18892d8ef316fb2a7eb2992c77/src/main/skills/bundled-skill-install/bundled-skill-classification.ts) hashes the tree). That is ADR 0009's "touch only the entries Timmy added" applied to a skill folder.

**Blocking versus waking.** `ask` "records the question and returns at once with `pending: true`"; the agent ends its turn and "Orca wakes you with the answer as mail"; `--wait` blocks instead ([`cli/orchestration.mdx`](https://github.com/stablyai/orca/blob/3ce8d75ae98c6d18892d8ef316fb2a7eb2992c77/docs/site/content/docs/cli/orchestration.mdx)). `orchestration send --to ... --subject ... --body "..."` returns a receipt. Orca's rule "Never poll" exists because a polling script "takes your mail". So Orca keeps the shell command short and moves the wait into its own delivery, the opposite of holding the call.

## Windows: how `timmy` resolves and whether it stays inert

- **Environment and PATH key.** The Windows environment block is sorted "case-insensitive[ly]" by name and has no duplicate rule stated ([Changing Environment Variables](https://github.com/MicrosoftDocs/win32/blob/docs/desktop-src/ProcThread/changing-environment-variables.md)). Timmy builds the PTY environment as `{ ...process.env, ...env }` (`electron/terminal/terminal-service.ts`). **Inference:** on Windows `process.env` enumerates `Path`, so adding a `PATH` key could create two keys that differ only by case; Orca's `resolvePathEnvKey` exists to avoid that, so Timmy should find the existing key case-insensitively before prepending.
- **PowerShell** (Timmy's default shells are `pwsh.exe` then `powershell.exe`): precedence is alias, function, cmdlet, then external executables; PowerShell "treats the file extensions listed in the `$Env:PATHEXT` environment variable as executable files"; a command in the current directory needs `.\` ([about_Command_Precedence](https://github.com/MicrosoftDocs/PowerShell-Docs/blob/main/reference/7.5/Microsoft.PowerShell.Core/About/about_Command_Precedence.md)). So `timmy.exe` and `timmy.cmd` resolve through PATH, an alias or function named `timmy` would win, and a `.ps1` depends on execution policy (Claude Code bypasses it by default; Codex and OpenCode were not checked).
- **Git Bash** (Claude Code's default Windows shell): in Cygwin's rules, which Git Bash descends from, "the .exe need not be included in the command", but "for programs that end in .bat and .com, you cannot omit the extension", and an extensionless script beats a same-named `.exe` ([Cygwin user guide](https://cygwin.com/cygwin-ug-net/using-specialnames.html)). **Inference:** ship `timmy.exe`, which every shell finds; a `.cmd` alone is unlikely to resolve as bare `timmy` in Git Bash. `.cmd` has the quoting limits Orca documents for message bodies.
- **Inert outside Timmy.** Putting the directory only in the PATH of Timmy's own PTYs, as Orca does, means a shell started elsewhere cannot resolve `timmy`. The cost is that a globally installed copy (what Orca also offers) would not be inert, and the command must still refuse when `TIMMY_TERMINAL_ID` is absent. The name `timmy` could collide with a binary the user already has; not checked. A login shell's startup files can reorder PATH (Orca's reason for `ORCA_CLI_COMMAND`); Timmy could export an absolute-path variable and have the skill use it.

## What this means for Timmy (inference, not sourced)

1. **One command can serve all three, but not through one mechanism for approval.** The allow rule is a different file and syntax per Provider (`~/.claude/settings.json` array, `~/.codex/rules/timmy.rules`, `opencode.json` object), all Timmy-owned entries or files in ADR 0009's sense. Codex's rule also removes the sandbox block, so on Codex the approval rule is not optional.
2. **Do not hold the shell call for the user's decision.** The limits above (2 minutes then background, 2 minutes then killed, 10 to 30 s then poll) are worse than #173's for MCP, and only the first can be raised without the model's cooperation. The map already lists "queued" as an outcome the Sender is told; the command can return `queued, awaiting approval` at once, as Orca's `ask` returns `pending`, and Timmy delivers or drops the Message when the user answers. That moves the approval prompt's "no answer in time means refused" rule off the Provider's clock entirely. It also means the Sender is never given the outcome after the fact unless it is a later Message, consistent with the map's one-way rule.
3. **Identity can ride the same environment variables as the Hook**, and #172's per-Terminal secret still applies. Orca shows the shape without the secret and its error text shows the cost. Choose the secret's variable name to avoid KEY, SECRET, TOKEN, PASSWORD and AUTH, which Codex's opt-in filter and Claude Code's scrub may remove; alternatively put the secret in the value of an endpoint variable (a per-Terminal socket or pipe path) and test it. The command must fail closed when the variable is missing, because Codex's user policy can drop it.
4. **A skill is the way the agent learns, and one file is not enough.** Install `~/.agents/skills/<name>/SKILL.md` for Codex and OpenCode and `~/.claude/skills/<name>/` for Claude Code (a symlink between them is allowed by Claude Code and followed by Codex), remove by deleting only that folder, and tolerate the user having edited it, as Orca's classifier does. A skill is visible in every session, so its description must say, as Orca's does with its counter-case, when not to use it, and the body should check `TIMMY_TERMINAL_ID`.
5. **Windows needs a real executable, an extensionless script for Git Bash, and a careful PATH edit.** And Message bodies must avoid shell quoting problems: Orca passes the body as an argument and ships `.exe` to avoid `cmd.exe` mangling; Codex's rule matching favours plain argument vectors over heredocs. A body passed on stdin is attractive for size and quoting but may defeat Codex's rule.
6. **Claude Code's own cross-session messaging overlaps this feature** and is on by default; the map should decide whether it matters.
